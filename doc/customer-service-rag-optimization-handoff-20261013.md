# 客服 RAG 优化交接文档

日期：2026-10-13。本文面向接手优化的 Agent，记录真实评测基线、待验证假设、执行顺序和交付要求。本文不是已完成优化的声明，也不授权删除知识文档、切换生产索引或清理容器数据。

## 1. 目标与边界

在固定 90 条产品评测集上，定位并减少可回答题误拒答，提升回答证据质量，并补齐同一次请求的检索、重排与拒答路径证据。保留已有权限约束、引用校验、服务故障处理和公共接口兼容性。

接手后先阅读根目录 `AGENTS.md`、`ai-service/README.md` 和本文。用户本次仅要求交接文档；后续修改实现或执行生产数据操作，应依据后续任务授权推进。不得为了提高指标直接改变答案预期、放宽安全边界或移除失败题。

当前知识分类是文档逻辑分类，仍使用单一客服索引。没有按分类自动过滤或多知识库路由；本轮优化不默认包含实现多库架构。

### 指标解释

本轮通过正在运行的 Python HTTP `/internal/v1/customer-service/answers` 测真实问答；每题回答后另做一次 embedding 与只读 Milvus 检索。因此 Recall/MRR/NDCG 是独立检索诊断，不是同请求轨迹，更不是重排后的成绩。

诊断最多取 8 个文本块，再按文档去重。现有严格引用函数要求可回答题有回答、有来源、来源文档无重复，且所有来源都在标注允许集内；无答案题须拒答且无来源。它不等于事实正确率或伪造引用率。

`annotations.json` 仍为源码对照、待人工产品验收状态。不要把 Agent 审查或模型裁判标记为人工审核。

已确认的实现细节：`_filter_and_dedupe` 在重排前按 chunk ID 和 document ID 去重，一份文档只保留第一个有效块。重排最多保留 3 个上下文；单块最多 1200 字符、总计 3000 字符，之后还经过提示字节预算裁剪。

优先验证三个假设：

1. 同文档后续更相关的块在重排前被淘汰，使管理说明、部署步骤等局部事实未进入模型上下文。
2. 有效事实在字符或字节预算裁剪后丢失，导致模型保守拒答。
3. 新正文、FAQ 与旧综合手册内容重叠，引发来源竞争或允许来源标注过窄。

阈值过滤也属于排查路径，但先读取非敏感运行配置确认是否启用。不得未经核对断言“阈值过高”。诊断召回命中不证明同一次 HTTP 回答拿到相同候选块。

## 6. 推荐执行顺序与阶段产物

### 阶段一：保留基线，补齐同请求证据

先确认服务状态、当前文档版本、摘要及旧手册状态。保护历史 JSON 和报告，给每次新运行分配独立 ID、输出路径和配置快照；仅记录必要非敏感设置。

为选定失败题增加可关闭、受控的同请求诊断，记录以下阶段信息：原始候选文档/块 ID 与排序，过滤/去重后候选，重排排名与分数，阈值后保留项，字符和字节裁剪后的上下文 ID 与长度，模型 answered 标志、引用校验结果和最终拒答原因。

区分空召回、过滤后为空、重排后为空、阈值筛空、上下文裁剪为空、模型明确拒答、模型调用/解析/引用校验失败。系统兜底不能算正确拒答。推荐默认只记录 ID、长度、稳定原因码；需要查看正文时使用受控评测资料，不向普通用户响应暴露内部追踪或完整提示词。

requestId 的关联需贯通 API 与服务，不通过共享实例可变字段保存单次追踪，避免并发串题。若改变内部签名，检查调用方和测试；公共问答响应保持兼容。

阶段产物：9 条误拒答和 3 条召回未完整覆盖题的原因表，每条提供阶段证据、已证实原因和仍不确定项。不得用另一轮独立检索代替同请求证据。

### 阶段二：按证据做小范围修复

若确认重排前文档去重丢失关键块，比较“保留不同块后重排，再控制文档多样性”等有限方案；通过相关测试验证重复块、同文档多个关键块、上下文预算、无效版本过滤及并发行为。不要预先指定该方案必然有效。

若确认正文或裁剪问题，优先按业务小节补充独立、完整的操作描述，保持当前能力与推荐规范清楚分开。正文修改走 Spring 上传/替换和异步索引流程，更新实际映射并核对摘要，不绕过 Spring 直接写业务数据库。

若确认阈值问题，再依据分数分布做对照实验，保留安全题拒答能力。不得直接移除阈值或绕过引用校验来提高回答率。

每次实验尽量只改变一类因素。保留原实现/配置以便回退，记录变更、版本和运行标识。

### 阶段三：来源与标注复核

对 38 条已回答但来源超出允许集的题逐条检查：实际引用是否覆盖 expectedFacts、是否含错误事实或越权指引、是否混淆规划与现状、非标注文档是否是合理补充。

输出复核表：样例 ID、实际来源、支持/不支持/待确认、证据小节、修正类别、审核身份。有效来源可补充标注；真实错误则修复正文、检索或回答。不得仅因“模型引用了它”就加入允许集。

若修改标注，保持 90 题及分类配额，递增 datasetVersion 并同步 annotations。用旧口径和新口径分别报告，解释变化；不能把新标注分数称作原基线同口径提升。旧手册仍需先盘点，再决定保留、替换或归档；当前没有授权删除或禁用它。

### 阶段四：全量对照与人工验收

对相同 90 个问题做完整复测，分别报告原始检索、重排、阈值/上下文损失、回答、严格引用和延迟；只有能取得同请求排名才填写重排指标。明确重排指标是阈值前还是阈值后，不混用。

复测比较配置、正文、标注版本和文档映射差异；服务错误、超时和系统兜底单列，不能计入成功拒答。不要只回归失败题就宣布全量通过。

建议人工检查全部 90 题，至少重点覆盖错误、权限和安全边界；记录检查样本数、逐条判定与错误理由。Agent 对照复核可先完成，但人工字段保持待审，直到获得真实人工评审。

## 7. 执行和验证注意事项

## 8. 验收和交付要求

保留原设计目标：Recall@8 ≥85%、MRR@3 ≥75%、NDCG@3 ≥75%、无答案准确率 ≥90%、严格引用通过率 ≥98%、人工抽检正确率 ≥85%。未测指标必须留空或标注未测，不认定通过。

本轮新增关注项为 9 条误拒答和管理知识 1/5 回答率，原设计没有独立数值门槛。建议追求减少误拒答并保持 9/9 安全拒答，但这属于优化方向，不能冒充用户已确认的新验收标准。9 条无答案题中 1 条错误就降至 88.89%，因此原 ≥90% 目标在该集合上实际要求 9/9。

使用全部样例调参后，结果只说明固定集合回归效果，不代表泛化质量。若需评估泛化，在现有 90 题内部预先划分调参与保留集合，不扩大用户限定的样本数，并注明是否已被此前实验使用。

交付至少包含：

1. 已证实原因与证据，和仍未验证的假设。
2. 变更文件、配置、正文/映射/标注版本，以及回退方法。
3. 90 题新旧对照指标、逐题差异和原始记录路径；标注变更单独说明。
4. 人工复核状态及仍未达标项，不以引用字段有效替代事实正确。
5. 验证命令和结果；任务相关 Git 提交哈希。

仅提交任务相关源码、测试和维护文档，不提交运行报告、日志、密钥、`tmp/` 或用户既有 `projects/`。按项目要求使用中文 Conventional Commits，提交前检查 `git status --short` 与 `git diff --check`。
