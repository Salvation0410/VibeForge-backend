## 4. 工作包 A：完整交错与 worker 提交确认测试

### A1. 同文档 B 发布后 A 晚提交

沿用隔离 MySQL、真实 Mapper/事务代理，增加仅测试使用的同步控制，优先包装现有边界而非给生产协议增加测试字段。

固定时序：

1. A 为文档 D 的 V1 准备完整候选，在调用发布事务前发出 reached 信号，等待 release。
2. 测试必须确认 A 已到暂停点；此时 A 不持有发布事务的数据库锁。
3. 按真实管理更新语义将 D 更新到 V2，产生 B；按现有 owner/lease 规则取得执行资格，B 准备并发布成功。
4. 通过独立数据库连接读取 B 发布后的持久状态作为比较基线。
5. release A，让它继续提交，并走完实际 worker 的异常处理及 finally 清理。
6. 再用独立连接核对数据库。

两个 latch 分别代表“已到达”和“允许继续”；所有等待有界，线程异常必须传回测试主线程。超时用于报错，不用于决定交错顺序。B 没有成功就立即失败，不能把任意异常当成 A 被正确拒绝。

同文档有效租约可能互斥。需要到期时使用可控时钟，需要撤销时走现有路径；不得偷偷改 SQL 绕过互斥后声称验证了正常执行。先核对管理更新是否推进 epoch、撤销租约，以及 B 的正常认领方式。

必查结果：

- 活动 publication、collection、snapshotHash 仍为 B。
- epoch 等于 B 发布后的基线，不因 A 再推进；不要硬编码“只增加 1”，管理更新也可能推进 epoch。
- D 的当前内容版本、已索引身份及状态仍对应 V2。
- B 的任务与不可变发布事实保持正确；A 没有新增发布事实或发布镜像 outbox。
- A 可以按真实规则写自己的终态，但不能污染 B 或 D。
- A 的迟到 finally 不得撤销替代执行的资格；若 B 完成后已无活动 lease，另用独立用例保留一个替代 lease 来验证，避免空断言。

当前 commit 先查既有事实，再查 owner/lease，随后查 epoch。完整场景可能先报 CLAIM/LEASE 失效，不能统一期待 EPOCH_CONFLICT，也不能接受任意异常。分别建立前置条件明确、错误码明确的所有权和 epoch 测试。

### A2. 事务内检查与写入之间的串行化

A 在真实事务取得权威行锁后暂停；B 发起同文档管理更新，确认无法越过锁；放行 A 后让两边结束，验证与实际提交顺序一致的状态。

此场景不能等待 B 先完成再放 A，否则人为死锁。不能仅凭短时间 Future 未完成证明数据库锁竞争；结合锁等待视图或实际 SQL 执行观测。环境权限不足时明确降低结论，不以 sleep 替代证据。

### A3. 提交成功、确认异常的真实 worker 集成

- 使用真实 worker、真实 MySQL/事务服务；Python 候选服务可使用计数替身。
- 测试包装层先调用真实事务代理，等待提交完成，再向 worker 抛连接异常。不要在事务内部抛错造成回滚，也不要用包住整例的回滚事务掩盖结果。
- 断言 worker 查到匹配事实，任务仍成功，无失败/重试覆盖，无再次准备候选，无重复 publication 和 epoch 推进。
- 另测事实查询不可用时不擅自写失败；这不是自动恢复承诺。
- 最后补一项真实 Milvus 集合的读取验证，A 结束后请求固定的仍为 B 集合。数据库层和跨资源层分别记录证据，不必让每个排列都调用 Milvus。

验收产物：测试命令、环境开关、实际通过/跳过数量、受控时序、前后状态摘要及覆盖边界。重复运行验证测试设施稳定，但重复次数不是遍历所有并发时序的证明。
