## 方案比较与推荐

### A：减少读取并增加交回验证条件，推荐

保留40次总额度、两次有限修复、完整批次校验及原构建/质量门禁。

1. **优先限制修复范围**：构建报告已给出父文件、组件和属性，修复提示明确优先读取 App.vue 与相关组件，必要时才读依赖数据；已成功补齐后停止无关全项目确认。生成提示同时强调父组件调用必须传齐 required props、导入导出保持一致。提示不能保证模型遵守，也不能据此跳过确定性检查。
2. **增加确定性的交回验证条件**：在正式修复已明确成功写入、没有待写文件且配图满足后，对写入后的连续纯读批次设上限，建议初值3批；同时在剩余工具数不多于4次时优先交回验证。仅在完整批次结束判断，绝不截断同批后续写入；这两项是待确认的策略参数，不是当前已实现默认值。
3. **交回之后仍走原验证**：先校验与强制构建，再质量审查；仍失败才在剩余全局额度和修复次数内继续。无成功写入、待写计划未完成、配图未满足或存在取消时，不得以预算理由伪装完成。若仍无额度完成下一次必要修复，应明确失败，不绕过门禁。
4. **补足中途诊断**：错误边界保存有界的阶段、累计数、读写计数、剩余预算及交回原因；明确“最后完成阶段摘要”和“失败现场计数”的差异。保持子图私有状态边界，不记录源码、模型正文或凭据，不新增自动恢复。

收益：不增加单请求工具上限，针对本次“写完后持续读”的路径收口，让构建负责判断修复是否有效。代价：合法的大范围依赖核对也可能提前交回，消耗一次验证/修复机会；需要覆盖无写入、待写文件、配图、混合批次、跨阶段累计、取消和 checkpoint 恢复的回归，不能承诺本次或所有应用必然成功。

### B：只调整提示，作为A的配套

改动小，可以减少模型读取倾向，但模型仍可能忽略完成与预算提示，无法确定性阻止同类耗尽。单独采用不能解决流程收口缺口。

### C：提高40次上限，暂不推荐

可能为合理的大工程多留空间，但成本、延迟和重复读取均可能同步增加。当前配置字段还限制 `le=40`，直接将 `.env` 改成60会配置校验失败；必须连同代码、成本和上下文策略一起评估。不是本次首选根因修复。

建议先确认A（包含B），在隔离 Fake 场景复现本次“新文件穿插重复读取”，证明原策略触发预算失败、新策略进入验证；再重启加载实际改动的 Python 服务，从新请求验收。若一并需要上轮 Java 锚点改动生效，还需确认 Spring 加载了对应构建。重启本身不修复本次策略缺口，也不恢复旧失败任务。

### 当前实现

`vue_tool_loop.py` 私有进度增加 `successful_write` 与 `read_only_batches`；只有本阶段 file_write/file_modify 的 `ok is True` 才设置成功写入标记。正式修复在完整批次结束后，将完整成功的纯 file_read 批次累计，混合批次或失败/未知/截断/超界读取重置。不同新文件同样计算开销，从而覆盖本次穿插新文件的路径。

本阶段明确成功写入、filePlan 无待写文件且配图满足时，连续三批纯读或全请求剩余工具不多于四次，即结束当前工具阶段并返回原验证。低额度也可在完整写入批次后触发；同批次第二个写入仍执行，不在批次中途截断。生成及内部兼容入口不启用，40次总上限、两次修复及整批工具校验保持。

`vue_budget.py` 统一完整有界读取判定和计数；预算拒绝日志按失败时子图现场记录实际累计和本阶段读写/其他工具数、修复序号、剩余额度、本批请求数与纯读批次。交回日志固定原因为 `READ_BATCH_LIMIT` 或 `LOW_TOOL_BUDGET`，原快照/重复读取原因继续保留。不记录路径、源码、工具参数或模型反馈，不修改 PostgreSQL 摘要结构；中途失败时摘要仍可能停留在上个完成阶段，应关联现场日志读取。
