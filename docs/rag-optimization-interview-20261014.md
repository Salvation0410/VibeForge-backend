# 客服 RAG 链路优化：秋招面试说明

## 一、项目背景

这是一个面向产品客服的 RAG 问答链路。用户提出产品使用问题后，系统从 Milvus 检索知识块，使用 BGE Cross Encoder 重排，再把有限数量的知识片段交给大模型生成回答，并返回来源引用。

本次优化使用固定的 `product-2026-10-12-v1` 评测集，共 90 道题：

- 81 道有知识依据、理论上应该回答；
- 9 道无答案或安全边界题，应该拒答；
- 知识库实际包含 81 个活动文本块，来自 11 份产品文档。

优化前最明显的问题是：检索结果中同一份文档的多个块会在重排前被提前去重，只保留第一个块。如果第一个块相关性一般，而后面的块才包含真正回答问题的操作步骤，后面的有效证据就永远没有机会参加重排。

## 二、优化前的链路和问题

### 优化前链路

```text
问题
  -> Embedding
  -> Milvus 召回 Top-8
  -> 按 chunk 去重、按 document 去重
  -> BGE 重排，最多返回 Top-3
  -> 字符/字节预算裁剪
  -> 大模型回答与引用校验
```

问题出在“按文档去重”的位置。原逻辑类似于：

```text
召回块 A：文档 D，第一个块，相关性一般
召回块 B：文档 D，后一个块，相关性更高

提前按 documentId 去重后：
只保留 A，B 不能参加重排
```

这会造成一种典型的误拒答：知识库中确实有答案，但最相关的知识块在重排前被丢弃，模型最后只能看到不完整或不匹配的上下文，于是回答“暂未找到足够依据”。

通过请求级诊断，我记录了每个请求的召回、过滤、重排、阈值、文档选择、字符预算、模型终态和引用状态。重点题中确认了管理知识上传、部署下载等问题存在 `duplicate_document` 丢块现象；没有证据表明主要原因是重排阈值或上下文长度预算。

## 三、为什么选择这个方案

我没有直接扩大 Top-K、放宽阈值、修改提示词或重写知识库，原因是这些动作会同时改变多个变量，实验结果难以归因，也可能降低安全拒答质量。

我选择了一个单因素、可回退的候选策略：

1. 召回后只按 `chunkId` 去重，不提前按 `documentId` 去重；
2. 最多保留 100 个有效候选，全部送入重排；
3. 重排结果只允许改变分数和顺序，正文、文档身份、版本和来源必须回到原始候选对象，防止供应商返回同 ID 的恶意替换正文；
4. 重排完成后，按分数选择每份文档的最高分块；
5. 最终仍最多保留 3 份不同文档；
6. 保持原有 1200 字符单块、3000 字符总上下文、UTF-8 字节预算、引用校验和安全拒答逻辑不变。

这个方案的核心思想是：**让重排器决定“同一文档中哪个块最相关”，而不是让检索阶段提前替它做决定。** 同时在最终上下文阶段保留文档唯一性，避免多个块来自同一文档而挤占来源名额。

## 四、优化前后指标对比

以下使用同一次 HTTP 评测方式建立基线和候选结果，避免把历史独立检索结果与新结果直接混比。

| 指标 | 优化前基线 | 优化后候选 | 变化 |
|---|---:|---:|---:|
| 可回答题回答数 | 71/81（87.65%） | 76/81（93.83%） | +5 题，+6.17 个百分点 |
| 11 道重点题回答数 | 2/11 | 7/11 | +5 题 |
| 管理知识回答数 | 1/5 | 3/5 | +2 题 |
| 安全/无答案正确拒答 | 9/9 | 9/9 | 保持 |
| 原始 Recall@8 | 96.30% | 96.30% | 不变 |
| 重排 MRR@3 | 83.54% | 88.07% | +4.53 个百分点 |
| 重排 NDCG@3 | 86.18% | 90.18% | +4.00 个百分点 |
| 重排 Coverage@3 | 93.83% | 96.30% | +2.47 个百分点 |
| 严格引用通过 | 41/90（45.56%） | 39/90（43.33%） | -2 题 |
| 平均延迟 | 2529 ms | 2587 ms | +2.29% |
| P95 延迟 | 3127 ms | 3117 ms | 基本持平 |
| 请求错误/降级 | 0/0 | 0/0 | 保持 |

优化后的回答覆盖和重排排序明显改善，但严格引用指标下降了 2 题。因此正确结论是“候选保留策略改善了证据进入模型的机会和回答覆盖”，而不是“整体质量指标全部提升”。严格引用下降主要来自回答引用了正文中确实存在、但不在原题目 `expectedDocumentIds` 允许集合内的额外文档；这不能通过直接扩大允许集合来刷指标，仍需要人工确认标注口径和回答针对性。

## 五、指标是什么意思，如何计算

### 1. Recall@8：前 8 个召回结果覆盖了多少目标文档

对每道题，标注中有一个期望文档集合 `G`，系统召回前 8 个结果得到集合 `R8`：

```text
Recall@8 = |G ∩ R8| / |G|
```

本评测中使用题目允许的目标文档作为参考，统计 90 道题的平均值。它回答的是：**答案相关文档有没有被召回。**

本次优化没有修改 Embedding、Milvus 查询或 Top-8，所以 Recall@8 前后完全一致。这也说明本次优化不是“召回能力变强”，而是“召回到的候选没有过早丢失”。

### 2. MRR@3：正确目标第一次出现得有多靠前

设第一条相关结果在第 `rank` 位，如果前 3 位没有相关结果，则记为 0：

```text
RR@3 = 1 / rank       rank <= 3
RR@3 = 0               rank > 3 或未命中
MRR@3 = 所有题目的 RR@3 平均值
```

例如，相关结果排第 1 名得 1.0，排第 2 名得 0.5，排第 3 名得 0.333。它更关注第一个正确证据是否靠前。

### 3. NDCG@3：前 3 个结果整体排序质量

NDCG 同时考虑多个相关结果和位置折损。先计算：

```text
DCG@3 = Σ (2^rel_i - 1) / log2(i + 1)
```

其中 `rel_i` 是第 `i` 个结果的相关性；再除以理想排序下的 `IDCG@3`：

```text
NDCG@3 = DCG@3 / IDCG@3
```

值越接近 1，说明相关证据越集中在前 3 位。相比 MRR，它不仅看第一个正确块，也看后续相关块的整体位置。

### 4. Coverage@3：前 3 个结果是否覆盖目标

本项目中用前 3 个最终结果覆盖目标文档的比例衡量：

```text
Coverage@3 = 命中目标文档的题数 / 有效评测题数
```

它回答的是：**最终真正进入上下文的前三个结果，还有多少题包含目标证据。** 本次从 93.83% 提升到 96.30%，说明后续更相关的块被保留下来的概率提高。

### 5. 可回答题回答率

```text
可回答题回答率 = 正确标注为可回答且模型实际回答的题数 / 可回答题总数
```

本次是 `76 / 81 = 93.83%`。它衡量模型有没有从“拒答”走到“给出回答”，但不等于回答内容一定完整或事实一定正确，所以必须配合人工事实验收和引用检查。

### 6. 严格引用通过率

本项目的严格口径要求：

- 可回答题必须实际回答；
- 必须存在来源；
- 来源文档不能重复；
- 所有来源文档必须属于该题标注的 `expectedDocumentIds`；
- 无答案/安全题必须拒答且不带来源。

计算方式为：

```text
严格引用通过率 = 满足上述条件的题数 / 90
```

它是自动化的引用契约指标，不等于人工事实正确率，也不等于“引用一定是伪造的”。本次有些回答引用了正文真实存在的额外文档，但因为超出原标注允许集合，仍按严格口径不通过。

### 7. 平均延迟和 P95

平均延迟：

```text
平均延迟 = 所有请求耗时之和 / 请求数
```

P95 是将请求耗时排序后，取 95% 请求能够完成的时间位置，用来观察长尾，而不是只看平均值。本次平均延迟略增约 2.29%，P95 基本持平，说明新增候选重排没有造成明显长尾恶化。

## 六、我是如何验证的

为了让对比可信，我做了以下控制：

1. 基线和候选都使用同一份 90 题数据集；
2. 两次运行的 81 个活动块正文逐块一致；
3. 11 份产品文档的版本和 SHA-256 与映射一致；
4. 模型、Embedding、重排器、Top-K、上下文预算和 alias 保持一致；
5. 候选只改变“文档去重发生在重排前还是重排后”这一因素；
6. 先执行 11 道重点题和 9 道安全题，再复用这 20 条结果补齐剩余 70 题，避免重复请求；
7. 记录每一次请求的阶段轨迹，确认没有请求错误、诊断缺失或降级；
8. 保留逐题差异和人工验收表，而不是只保存聚合指标。

## 七、面试中可以这样回答

> 我负责过一个客服 RAG 链路的优化。原链路是 Milvus 召回 Top-8，再按文档去重后做 BGE 重排，最后把 Top-3 上下文交给大模型。通过请求级 trace，我发现一个具体问题：同一文档的第一个召回块相关性一般，但后面的块才包含真正的上传、部署或权限步骤；由于文档去重发生在重排前，后面的块根本没有机会被模型看到。
>
> 我没有直接放大 Top-K 或放宽阈值，因为那会同时改变多个变量，也可能损害安全拒答。我采用了单因素修复：只按 chunk 去重，让同一文档的候选全部参与重排；重排后再按文档选最高分块，最终仍限制最多 3 份文档，并保持字符预算、引用校验和安全边界不变。
>
> 在同一份 90 题评测集上，可回答题回答率从 87.65% 提升到 93.83%，11 道重点题从 2 道提升到 7 道，重排 MRR@3 从 83.54% 提升到 88.07%，安全拒答保持 9/9，P95 延迟基本不变。与此同时，严格引用从 41 题下降到 39 题，说明回答覆盖提升不代表整体质量全部提升。通过逐题复核发现，部分回答引用了正文真实存在但不在原标注允许集合内的额外文档，另有两题存在回答针对性问题，所以我没有直接扩大标注允许集合，而是把它们保留为人工验收和下一步优化项。

> 这个项目让我比较重视两点：第一，RAG 优化要先用同请求证据定位损失发生在哪一层；第二，指标必须分层看，召回、排序、回答率、引用契约和人工事实正确率不能互相替代。

## 八、面试追问准备

### 为什么不直接把 Top-K 从 8 调到 16？

因为当时证据指向的是“候选被错误去重”，不是“目标文档没有被召回”。先修复候选保留可以保持召回成本和变量数量不变。如果未来仍发现目标文档在 Top-8 之外，才适合单独设计 Top-16 实验。

### 为什么最终还要按文档去重？

知识块是文档的局部片段。如果最终三个上下文全部来自一份文档，可能挤占其他来源，也会影响引用唯一性和回答覆盖。因此让同一文档内部先竞争，最终阶段再限制不同文档数量。

### 为什么严格引用下降仍然保留这个优化？

因为它确实改善了“有证据却误拒答”的问题，并且安全拒答没有退化。但严格引用下降说明还存在标注口径和回答针对性问题，所以这是一个已验证有效的候选保留修复，不是“全部指标达标”的最终方案。下一步应先完成人工事实验收，再决定是修正文档、修标注，还是调整引用选择策略。

### 这能证明泛化到所有问题吗？

不能。当前只在固定 90 题集合上做了一次基线和一次候选对照，真实模型还存在随机性。它能证明该固定集合上的行为变化，不能直接证明统计显著性或泛化能力。

### 你认为下一步最重要的工作是什么？

先完成 90 题人工事实验收，重点确认回答是否完整、来源正文是否支持、是否存在权限或产品边界误导；然后针对严格引用下降的原因设计单因素实验，而不是直接扩大允许来源或针对具体题目做特判。

## 九、项目结果边界

- 已完成：请求级诊断、同请求 HTTP 基线、候选保留修复、20 题候选验证、90 题全量对照、逐题差异记录。
- 已证明：候选块过早按文档去重会损失部分有效证据；延后文档去重能提高固定集合的回答覆盖和重排指标。
- 尚未证明：人工事实正确率提升、严格引用目标达成、对更大题集的泛化能力。
- 当前最诚实的项目结论：**回答覆盖和证据排序得到改善，但引用契约和人工事实质量仍需继续验收。**
