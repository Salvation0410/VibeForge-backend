# 冻结输入的 cap1/cap2 答案对照

## 本轮授权与选择

用户在第十四轮交付后要求继续下一轮，接受上轮已提出的固定输入、仅改变配额的真实答案对照路线。本轮先实现可审阅的设施并离线验收；没有取得新的具体供应商调用额度。真实运行必须等设施、计划和预算请求准备好，再单独取得用户对最多 180 次新回答的确认。旧授权锚点、报告及生产 `.env` 均不改。

推荐两组重新回答，复用第十二轮已经冻结的候选、查询向量及 BGE 顺序。只新增 90×2 次回答，不增加 Embedding、BGE 或 INDEX。复用历史 cap1 答案只调用新 cap2 虽少花 90 次，但引入模型时间漂移；重新在线召回会增加资源与候选变化，妨碍配额单变量解释。本轮采用推荐路线，不改变生产选择策略。

复用正式 `CustomerServiceRagService`、已有 `answer_once` 与 `_runtime_model`。两组都显式使用缓存的开启重排路径，分别设置配额 1/2；每题顺序交替，单并发。预备阶段用 Fake Model 生成两组实际最终 contexts，并与第十三轮冻结上下文逐字核对。live 的模型包装层在发送前再次比对问题及完整 contexts，变化即拒绝发送。来源、字符/实际 JSON 字节和严格解析继续由正式路径处理，不修补坏 JSON 算成功。

该实验使用历史冻结 publication，不访问当前 Spring/MySQL/Milvus，也不声称复核当前活动快照或两次在线 E2E。记录源快照、实现文件 hash、准备/运行代码 SHA、配置、提示及来源指纹；真实报告保存实际消息、原始响应、usage、结束原因及回答耗时，原始内容只留忽略目录。

## 默认离线、准备与额度

新增 `rag_cap_experiment.py`，默认只读离线验证；`--prepare` 在新的 tmp 子目录创建 `plan.json` 和 `authorization-request.json`。后者 `decision=pending`，绑定计划指纹、输出位置及固定上限 180，不代表用户批准。准备阶段不构造供应商客户端、不创建真实授权锚点、不发送请求。

`--live --plan ... --approval ...` 必须验证 `decision=approved`、study、计划指纹及整数 180，拒绝额外字段、布尔额度、错计划、配置/实现/输入漂移。软件只校验批准文件的结构及绑定，不能认证批准人；Agent 只能在收到可信用户明确答复后写入 approved。全部检查及输出目录/旧锚点拒绝发生在供应商初始化前。

新增 `rag_cap_budget.py`：固定锚点独占新建，不接受任意锚点或绕过额度的 study。每次发送前 flush/fsync 持久预占，失败、取消和进程退出均占用；未知/重复 key、超过 180、重启/换输出目录和持久化不确定均拒绝。没有 Embedding 预占接口。SDK `max_retries=0`，没有付费裁判、自动重试或续跑；三次连续供应商失败停止，未运行项保留。

发送前已保存全部 180 个占位。每次结果立即写盘，失败仍在每组 90 分母；取消保留当前错误及剩余 not_run，传播原取消。复用已验证的逐资源收尾保护；报告写盘或一个 closer 失败不能跳过其余客户端和账本清理。需要时仅给 `_finish_run` 增加兼容默认值的错误码参数，不重构旧真实实验。

## 盲审与结论

扩展 `rag_blind_review.py` 的固定 study 注册表，旧 study 仅接受 rerank_off/rerank_on，新 study 仅接受 cap1/cap2。评审 schema 接受这两个显式 ID，未知 study 或交叉 arm/包/映射/评审文件拒绝；不根据任意输入动态授予组别。保留旧输出和统计键，新组别输出 cap2MinusCap1 与 cap1Only/cap2Only，不能冒充重排开关改善。

公共包只投影问题、事实、实际 contexts、答案及来源，不含组别/配额/分数/耗时；私有映射独立保存。全 180 卡和模板可导出，pending 不产生质量提升值；代理和人工分开。原标注与支付澄清的 hash 分别绑定，新标准不静默覆盖旧标准；支付语料仍不发布，后续真实结果需另列现口径复核。
