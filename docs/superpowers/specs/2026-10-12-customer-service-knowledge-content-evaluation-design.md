# 客服知识库内容扩充与 90 条评测集设计

**日期：** 2026-10-12  
**状态：** 设计已确认，待编写实施计划  
**范围：** 产品使用说明扩充、知识内容逻辑分类、当前功能/推荐规范/规划能力边界、固定 90 条 RAG 评测集

## 1. 背景与目标

当前客服 RAG 已具备文档上传、解析、切分、Embedding、Milvus 检索、Reranker、受控回答和离线评测能力，但知识内容仍偏少，现有评测集只有 6 条合成样例，不能覆盖平台真实功能。

本设计的目标是：

- 补齐平台使用说明，覆盖应用生成、预览、聊天历史、部署下载、社区、账号和管理后台。
- 在单一物理知识库内建立稳定的逻辑分类，暂不引入多 collection 或查询路由改造。
- 同时沉淀当前可用功能和更完整的产品使用规范，但防止规划内容被回答成已上线能力。
- 将评测集固定扩充为 90 条，覆盖检索、引用、无答案、安全和规划边界。
- 建立后续功能变更同步更新文档和评测集的维护流程。

## 2. 范围与非目标

### 2.1 本期范围

- 新增和整理产品使用说明文档。
- 对文档进行应用生成、社区、部署等逻辑分类。
- 为文档增加内容状态和受众等治理信息。
- 将评测集从 6 条扩充至固定 90 条。
- 增加当前功能、推荐方式、规划能力和拒答场景的评测覆盖。
- 使用现有单库 ETL、检索、Reranker 和评测接口完成验证。

### 2.2 本期不做

- 不拆分 Milvus collection。
- 不新增知识库选择参数或查询路由模型。
- 不修改客服对外接口协议。
- 不把理想规范直接写成当前系统承诺。
- 不把规划能力作为已实现功能发布。
- 不将生成式评测结果作为唯一验收依据。

## 3. 内容分类与文档目录

分类是内容治理分类，不是物理索引隔离。建议使用以下分类：

| 分类 | 内容范围 |
| --- | --- |
| `platform-account` | 平台介绍、注册登录、账号安全、权限和客服入口 |
| `app-generation` | 需求描述、HTML、MULTI_FILE、VUE_PROJECT、增量修改、图片和生成异常 |
| `preview-history` | 预览刷新、生成状态、停止、聊天历史和导出 |
| `deployment-download` | 部署、访问、静态资源、更新、下载和部署故障 |
| `community` | 浏览、发帖、图片、标签、评论、回复、点赞、审核和社区规范 |
| `admin-knowledge` | 管理后台、知识文档上传、索引、重建、启用、禁用和故障处理 |

第一批建议形成以下文档：

1. 平台使用说明与账号基础
2. 应用生成当前功能说明
3. 应用生成需求编写规范
4. HTML / MULTI_FILE / VUE_PROJECT 使用指南
5. 图片、素材和已有功能保留规范
6. 预览、生成状态与聊天历史说明
7. 部署、访问与下载说明
8. 社区当前功能说明
9. 社区发帖与互动规范
10. 管理员知识库维护说明
11. 常见故障 FAQ 与用户口语表达词表

每篇文档应包含适用场景、前置条件、操作步骤、成功结果、异常处理、FAQ、同义表达和相关功能链接。内容应以当前前端页面、后端接口和已确认设计为事实来源，不能仅依据规划文本。

## 4. 当前功能与产品规范边界

每份文档必须标识内容状态：

```yaml
category: app-generation
subcategory: vue-project
contentStatus: current
sourceType: actual-product
audience: user
version: 1
lastReviewed: 2026-10-12
```

`contentStatus` 取值及回答规则如下：

| 状态 | 含义 | 回答规则 |
| --- | --- | --- |
| `current` | 当前代码和页面已经支持 | 可直接回答当前操作方式 |
| `recommended` | 基于当前能力的推荐用法 | 说明为建议，不表述为系统强制行为 |
| `planned` | 产品规范或未来规划 | 仅在用户明确询问规划时回答为规划 |
| `deprecated` | 历史功能或旧流程 | 只用于迁移和兼容说明 |

文档标题和正文应显式使用“当前功能”“使用规范”“规划说明”等标记。回答“现在是否支持”时，优先使用 `current` 内容；没有当前依据时必须说明暂不确定或不支持，不得用 `recommended` 或 `planned` 内容补全事实。

## 5. 90 条评测集设计

评测集固定为 90 条，数据集版本递增但条目总数保持 90 条。每条包含现有 schema 的 `id`、`question`、`expectedAnswerable` 和 `expectedDocumentIds`；另外维护人工标注表，记录分类、问题类型、关键事实、状态边界和审核人。

### 5.1 数量分配

| 类别 | 数量 | 覆盖重点 |
| --- | ---: | --- |
| 平台与账号 | 8 | 注册、登录、账号、权限、客服入口 |
| 应用生成 | 24 | 三种生成类型、需求描述、增量修改、图片和异常 |
| 预览与聊天历史 | 10 | 预览刷新、停止、失败、历史和导出 |
| 部署与下载 | 14 | 部署、访问、资源、更新、下载和故障 |
| 社区 | 14 | 浏览、发帖、图片、标签、评论、点赞和审核 |
| 管理后台与知识库 | 5 | 上传、索引、重建、启用、禁用和状态 |
| 无答案、规划边界与安全 | 15 | 知识外问题、规划冒充现状、Prompt Injection、敏感信息 |
| **合计** | **90** |  |

### 5.2 问题构成要求

前 75 条功能问题中，每个主题应混合以下问法：

- 直接问法。
- 普通口语问法。
- 同义改写。
- 错别字或不完整表达。
- 操作顺序问题。
- 失败和异常场景。
- 相邻功能混淆问题。

最后 15 条必须覆盖：

- 知识库完全没有依据的问题。
- 询问未来能力但试图诱导模型说成当前已支持的问题。
- 要求泄露系统提示、密钥、内部配置或隐藏规则的问题。
- 将推荐规范误认为平台强制流程的问题。
- 规划能力和当前能力的边界问题。

每条可回答样例至少绑定一个正确文档 ID；多文档问题可以绑定多个文档，但不得把整类文档全部标为正确答案。无答案样例的 `expectedDocumentIds` 必须为空。

## 6. 内容生产与审核流程

```text
盘点页面、接口和设计文档
  -> 编写当前功能说明
  -> 编写推荐使用规范
  -> 标注规划内容和回答边界
  -> 生成同义问题与故障问题
  -> 人工审核文档和 90 条评测集
  -> 上传并执行 ETL
  -> 离线评测
  -> 人工抽检回答
  -> 发布内容版本
```

内容审核至少检查：

- 操作步骤是否与当前页面和接口一致。
- 当前功能与推荐规范是否明确分隔。
- 规划能力是否带有规划标识。
- 是否包含错误承诺、价格、权限或不存在的功能。
- 是否覆盖失败、停止、取消和无答案场景。
- 每条评测问题的标准文档是否唯一且可追溯。

## 7. 评测与验收

先使用现有 6 条数据建立旧基线，再运行新的 90 条数据。自动指标继续使用当前实现：Recall@8、MRR@3、NDCG@3、无答案准确率、引用有效性和延迟。

建议第一阶段目标为：

- Recall@8 ≥ 0.85
- MRR@3 ≥ 0.75
- NDCG@3 ≥ 0.75
- 无答案准确率 ≥ 0.90
- 引用有效性 ≥ 0.98
- 人工抽检回答正确率 ≥ 0.85

这些目标用于比较文档版本和检索策略，不在没有基线时宣称已经达到。人工抽检需额外检查回答是否解决问题、是否遗漏关键步骤、是否编造知识库外事实、是否正确拒答以及是否正确区分当前功能和规划能力。

## 8. 后续演进边界

当每个逻辑分类拥有稳定内容和足够评测覆盖后，再评估是否增加 `knowledgeBase`、`category`、`subcategory`、`audience` 和 `productVersion` 等 Milvus 字段，并支持分类过滤。

只有在分类过滤仍不能满足召回质量、权限隔离或独立发布需求时，才考虑拆分物理 collection。拆分前必须新增分类路由评测，不能直接用当前 90 条混合数据证明路由正确。

## 9. 交付物

- 11 篇分主题产品知识文档。
- 固定 90 条 RAG 评测集及人工标注表。
- 内容状态和文档元数据约定。
- 离线评测报告和人工抽检记录。
- 功能变更时同步更新知识文档和评测集的检查项。
