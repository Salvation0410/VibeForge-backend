# 生成租约迟到释放的所有者隔离

## 任务与现有证据

承接结构化编辑真实验收交接第 20 节，用户授权评估并执行下一步优化。本轮选择同应用请求竞争中的 Spring 租约释放边界。已有 `GenerationTaskResourcesIT` 覆盖不同 Redis 客户端的旧请求释放，以及未失锁时同客户端重入拒绝；尚未覆盖失锁后同客户端、同线程的新租约及异步解锁迟到。

原实现的 Redisson 应用锁所有者为客户端 ID 加 Java 线程 ID。同一线程可先后处理不同请求；旧请求释放时虽不删除新请求状态，却仍以原线程 ID 异步解锁，可能释放后继请求的锁。本轮先用下述两个真实资源时序取得失败证据，再实现逻辑 owner 隔离，结果见交接第 21 节。

## 方案选择

1. 仅按状态键匹配决定是否解锁：代码少，但不能隔离已经发出、随后迟到的解锁命令，状态读取失败也存在边界。
2. 在 transition lock 内等待解锁：缩小正常时序窗口，但失锁、延迟命令和线程身份复用仍需保护。
3. **每次获取分配独立 Redisson 所有者标识（采用）**：使用显式 owner 的 `tryLockAsync(long)` 与 `unlockAsync(long)`；即使同客户端同线程、命令迟到，也不能匹配新租约。

进程内静态计数器分配负 long，不与正 Java 线程 ID 混用，达到下界时失败关闭而不循环复用。客户端本身已有独立 ID，进程重启不会继承旧客户端身份。`GenerationLease.ownerThreadId` 保留内部字段名称但注明其为逻辑 owner。Redis 键、watchdog、立即拒绝语义、MySQL fencing/仲裁/台账与公共协议保持现状。

## 确定性测试

- 后继已持锁后调用旧 release：同客户端、同线程取得前后租约，显式失效旧测试锁；等待旧 unlock future 完成后检查新 owner、状态和第三请求拒绝。
- 旧 release 的解锁命令延迟：在实际 `unlockAsync` 调用边界捕获 owner 和 promise，旧锁失效、新租约建立后才把原命令交给真实 Redis，并排空结果。不能用 sleep 选择时序。
- 两种时序均核对旧取消/旧提交被拒绝、新请求仍可提交，以及任务/代际没有被迟到释放改写。
- 常规单元验证 owner 分配、显式 owner 获取/释放、签发或镜像初始化异常按同一 owner 释放，保留已有取消与提交回归。

测试使用现有真实 MySQL/Redis opt-in 夹具，随机 appId/requestId，只清除自身行与精确 Redis 键，finally 排空捕获的命令。模型与 HTTP 不参与，不修改生成目录，不恢复任何真实任务。

## 边界

这不是跨标签浏览器验收，也不修改当前按 appId 取消活动请求的 API。旧设计声称此 API 自然防止旧页面取消新请求，缺少客户端请求绑定支撑，后续应独立评估；本轮不能据租约测试扩大该结论。不实现自动认领、SSE 重连、Vue 回滚或任意长期并发保证。
