# 持久化取消与静态发布仲裁

用户已确认本阶段先实现取消权威状态，再推进所有者、心跳与恢复。

## 权威状态

新增 MySQL `generation_arbitration`，每个请求保存 appId、fencing token、ACTIVE/CANCELLED/COMMITTING 及首次取消时间，不保存输入或源码。签发代际时在同一事务插入请求绑定；取消、提交占位及最终激活均先锁定同一应用代际行，再检查请求绑定和决策。代际过期拒绝操作，终态不可逆。

取消先胜出时持久化 CANCELLED，最终激活必须拒绝；提交先持久化 COMMITTING 后取消不再胜出。COMMITTING 是提交资格，不是已发布事实，实际发布仍以 generation_publication 为准。发布失败不自动撤销占位，避免结果不确定时重新开放取消或重复执行。事务确认丢失时调用方失败关闭，查询独立发布事实，不自动恢复。

## Redis 与任务查询

Redis 继续串行化实时入口及发送引擎取消；先完成数据库仲裁，再更新 Redis 镜像。镜像写失败不否认已获胜的取消，仍通知引擎。数据库不可用时不报告取消成功，不调用发布动作，返回脱敏稳定码。任务查询从持久化仲裁补充取消时间；租约到任务插入的窗口仍由启动后复核保护。显式取消仍要求现存应用所有权和活动请求，不增加无租约恢复入口。

## 边界与验收

HTML/MULTI_FILE 最终激活受仲裁保护；Vue 没有不可变发布，取消仍是协作式，不承诺停止后不存在在途文件写入。人工恢复也绑定代际与请求。无 Python、NDJSON/SSE 和前端协议修改，不开放自动恢复。

升级所有 Spring 实例前执行独立增量迁移；保留历史仲裁记录，不在运行时清理取消墓碑。H2 执行真实 Mapper XML 验证取消/提交两种顺序、请求隔离、并发唯一赢家及重建服务；Redis mock 验证镜像失败仍通知及数据库失败关闭。执行干净 Java 编译与限定回归，真实资源测试仅在实际执行时报告通过。
