# 真实验收发现的终态与 checkpoint 收尾竞态

本轮用户要求继续完成真实端到端验收，并取消模型次数上限。HTML/MULTI_FILE 的真实请求可成功，但既有日志重复出现 PostgreSQL 事务清理告警。

离线门闩测试确认 `GenerationWorkflow.stream` 会在 `_execute` 完成之前投递成功/失败终态；消费者收到终态关闭流时，finally 会取消仍在图写入/清理中的任务。此时序是已复现缺陷；不能仅凭此认定所有 PostgreSQL 告警有相同根因。

采取最小变更：流边界暂存最终 completed/failed，继续等待队列结束及后台任务完成后发送。非终态事件仍实时返回，事件内容、公共 SSE 协议、发布规则及模型预算不变。清理异常仍按原行为记录，不改写业务终态。用户主动取消、真正传输断开仍沿用现有取消流程；重复取消问题需按真实复测证据另行处理。

验证：先运行成功/失败两种门闩回归确认旧代码失败，再验证修复通过和已有流式/取消测试。执行 Python 全量离线检查，重启 Python 后运行三类真实成功与取消请求，分别记录重启前后日志，不把历史通过结果改称修复后结果。

## 后续维护：重复取消与传输断连

原终态等待只消除了“收到终态立即断开”的窗口。后续确定性测试复现重复停止、消费者重复取消打断异步退出，以及 ASGI 发送失败未等待迭代器关闭的问题。上文真实模型复测属于上一轮，本轮优先使用门闩和真实 PostgreSQL 删除事务验证。

采用当前执行所有者绑定的收尾状态：终态内部入队前同步标记，覆盖图最后写入；无终态的异常路径也在 finally 标记。首次取消继续中断执行，任务已有取消请求或进入收尾后不再注入取消。后台任务由唯一消费者排空，asyncio shield 防止直接重复取消，AnyIO CancelScope 防止 ASGI 取消作用域在每个等待点重新取消。外层取消延迟到排空后继续抛出，不以吞掉取消伪造成功。

HTTP 路由用 aclosing 管理工作流；生成专用 StreamingResponse 在发送结束/失败后显式关闭响应迭代器。这样同时覆盖 ASGI 2.3 的 disconnect 通知与 2.4 的发送异常，且不改其他客服响应。注册冲突时取消尚未启动的新任务；流 finally 以执行对象核对归属，异常收尾仍释放登记和取消标记。

未采用延时重试（依赖机器速度，不能证明事务已退出），也未新增固定收尾超时（会重新截断事务，需要独立超时/恢复设计）。测试关闭门闩是明确的测试操作，生产没有自动恢复、认领或强杀能力。数据库永久挂起、进程退出、跨实例并发和直接 run() 的任意重复取消不在保证范围内。

验证组合：合成模型退出门闩、成功/失败终态门闩、清理失败与观测异常、登记冲突/迟到所有者、真实 ASGI 路由的两类断连；另用真实 PostgreSQL 官方 saver，在删除事务提交前注入重复取消，以独立连接核对物理记录清空和池可用。后者仍为 Fake 模型/工具，不能称为自然模型或浏览器端到端结果。
