# RAG 证据完整性与知识版本迭代方案

> 本文是源码分析、评测证据整理及后续实施方案。按任务逐项执行与验证；本轮不实施生产行为变更。日期：2026-11-13。

**目标：** 优先消除知识版本操作的契约冲突，再提高有效证据完整性，用可归因的评测决定检索参数与提示调整。

**架构：** Spring 继续拥有业务文档、OSS 对象登记及发布仲裁；Python 负责解析、索引、检索和回答。建议将内容版本、索引代际、全库发布版本分开，读取绑定明确发布快照，使用不可变索引和条件发布处理跨资源故障。

**技术栈：** Spring Boot、MySQL Outbox、OSS、FastAPI、LangChain 文档切分、Milvus、Embedding、BGE Cross Encoder。

## 1. 结论及证据等级

1. 当前本地知识正文的主要问题是章节语义与证据选择，不宜先盲调 chunk size。11 份 Markdown 的 72 个章节全部短于 300 字符，四组切分参数得到相同正文和定位哈希。
2. 同文档多块已经全部参与重排；后面的“一个文档只留最高分块”仍会损失互补事实。离线合成案例已复现；历史求助模板题也有相关证据缺失，但不能将所有拒答都归因于此。
3. 当前 Spring 操作定义与 Python 不可变版本身份存在冲突：重新索引、禁用后启用、重建后重新索引均有明确拒绝路径。应先作为正确性问题修复。
4. 原 90 题和后续 23 题固定上下文实验能支持局部结论，不能代表今天的知识快照或全体事实正确率。新集已生成，人工复核和真实问答尚未执行。

| 等级 | 本轮证据 | 能证明什么 |
|---|---|---|
| 源码核对 | Java 服务/Worker/Mapper、Python ETL/RAG/Milvus | 当前实现的规则与可到达拒绝路径 |
| 新鲜离线执行 | 本地正文切分；Fake Milvus 版本探针；合成候选选择 | 这些输入下实际函数行为，不是线上 API 验收 |
| 历史真实资源实验 | 2026-10-13 的配对 90 题、2026-10-27 固定上下文实验 | 当时配置与样本中的效果，不能外推到当前索引 |
| 未执行 | 新集模型问答、真实跨系统生命周期、多实例故障注入 | 只提出预期与测试方法，不报告成功率 |

离线结果存放于 `docs/superpowers/evaluations/2026-11-13-rag-offline-observations.json`；补充评测定义存放于同目录的 `2026-11-13-rag-boundaries.json`。临时探针源文件及输出位于 `tmp/rag-analysis-20261113/`，不作为生产运行器。

## 2. 当前切分策略

源码：`ai-service/src/ai_service/orchestration/document_etl.py`，主要入口 `_parse_markdown`、`_parse_txt`、`_parse_docx`、`_parse_pdf`、`split_sections`。

| 格式 | 先解析成什么 | 关键边界 |
|---|---|---|
| Markdown | 按 # 到 ###### 标题分章节，标题栈进入 locator | 标题不自动加入正文；代码围栏中的标题跳过，复杂混合围栏需另测 |
| TXT | 按空行分段，记录行范围 | 独立段落之间不合并、无跨段重叠 |
| DOCX | 普通段落各成 section，Heading/Title 样式用于定位；表格按行解析 | 同章多段不自动合并；表头不会自动附到后续行；合并单元格处理不等于完整表格语义重建 |
| PDF | pypdf 按页提取文本 | 无 OCR；扫描页可能 EMPTY；跨页无重叠，列顺序及表格布局不保证；加密文件拒绝 |

各 section 再独立经过 `RecursiveCharacterTextSplitter`：默认 **1000 字符、150 字符重叠**；分隔符依次为双换行、换行、`。`、`！`、`？`、`；`、空格、空字符串。准确代码列表是 `["\n\n", "\n", "。", "！", "？", "；", " ", ""]`，没有英文句点。这里是 Python 字符长度，不能当成 token 或 UTF-8 字节。

清洗包含 Unicode NFC、换行归一、控制字符及空白处理。逻辑 chunk ID 是 `documentId:documentVersion:chunkIndex`；Milvus 物理身份还包含 ETL 与模型信息。

**本轮实测：** 11 份本地正文，72 section / 72 chunk；长度 66–230 字符，平均 122.32，总计 8807。`300/50`、`600/100`、`1000/150`、`1400/200` 四组正文及 locator 的规范化 SHA-256 均为 `7a156cfa7a19abd4f336f456d9cded173f9e7f96fdd163af4b08a50dc26e1229`。所以仅调这些参数对该语料没有变化；此结论不涵盖未来长 PDF/DOCX。

## 3. 当前检索与回答策略

```text
问题 → query embedding
     → 解析 Milvus alias 为物理集合
     → COSINE dense Top-8，active chunk 过滤，Strong consistency
     → manifest / tombstone / 当前版本及物理 chunk 身份校验
     → chunkId 去重、元数据与有限分数校验
     → BGE 对全部有效候选重排
     → 可选重排阈值
     → 每文档仅留最高分块，最多三个不同文档
     → 字符与 JSON 字节裁剪
     → R1 回答提示 → 严格来源结构校验 → 公共回答
```

默认向量模型 `openai:text-embedding-3-large`，3072 维；重排模型 `BAAI/bge-reranker-v2-m3`，本地 CUDA Cross Encoder。索引代码没有明确配置 ANN 索引类型，本轮未检查真实索引元数据，因此不宣称具体使用 HNSW 或 IVF。

目前没有 BM25 混合检索、查询分解、父块回取或相邻块扩展。Embedding 和重排使用正文，没有标题前缀；回答模型得到 chunkId 与正文，locator/文档标题没有自动成为模型上下文。

重排 sigmoid 分数不是校准后的相关概率；默认不设阈值。重排故障可按原检索顺序降级；设有重排阈值时不能拿 cosine 分数冒充重排分数，相关故障会拒答。禁用重排与故障降级语义不同。

上下文硬限制：最多 3 段、单段 1200 字符、总计 3000 字符，最终 JSON 默认最多 16384 UTF-8 字节；超限会前缀裁剪。单纯把 finalTopK 改到 5 或增大字节预算，不会自动取消其他硬限制。来源最多 3 个，须是本次实际提供的唯一 chunkId；这能验证来源结构，不能证明每个结论被该来源支持。

默认 R1 区分“解释公开能力边界”与“执行越权或不可用动作”。内部真正拒答要求 false/空正文/无来源；公共接口展示固定非空拒答文案。因此公共拒答有文字不等于契约失败。RAG 当前为单轮问答，无跨请求记忆。

**检索边界：** Strong 只保证 Milvus 的一致性，不保证 MySQL/OSS/Milvus 原子一致。Top-8 后的版本校验会减少候选，当前没有补召回；trace 中 retrieved 也已经过 store 校验，不是原始 ANN 全量候选。每个文档 manifest/墓碑/块完整性检查带来额外 RPC，优化应先测耗时。读路径未显式核对 query 模型签名与集合模型签名；同维换模型的错误召回风险需真实资源测试。

## 5. 当前知识版本迭代设计及问题

### 5.1 已实现的保护

- Spring 新文档：documentVersion=1、indexedVersion=0、etlVersion=1；替换增加内容版本与 ETL；重新索引/启用仅增加 ETL；禁用/软删除增加 ETL并发送 DELETE。
- MySQL Outbox 异步任务、过期认领及版本条件落账；默认轮询 5 秒、任务认领约 60 秒、请求超时 30 秒、变更租约 45 秒，最多 5 次重试并退避。任务结果和文档索引完成由事务收尾。
- MySQL 协调器签发 HMAC 租约和 fence；同文档 INDEX/DELETE 冲突，全库 REBUILD 与全部文档变更租约冲突；Python 多处验证当前资格。租约目前没有续期。
- Milvus 单版本先写 inactive chunk，校验完整 manifest 后激活并收敛旧版；墓碑禁止被删除内容版本复活；相同身份与内容可幂等重试。
- 全库重建写 staging，核对计划指纹、完整块与 manifest 后再切 alias；相同操作可识别已发布目标；切换前失败通常保留旧 alias，切换异常用读回判断，可能存在不确定结果。
- 清理默认保留两代，宽限 120 秒、扫描和清理有界、所有权不确定时保留。清理依附重建触发，并非定时保证磁盘恰好两代。

### 5.2 需要优先修正的契约

| 操作/边界 | 当前原因与行为 | 证据状态 | 建议 |
|---|---|---|---|
| 相同输入重试 | 版本、ETL、模型、内容一致，可幂等 | Fake 已执行 | 保留，重试不得换索引身份 |
| 重新索引同一内容版本 | Spring 换 ETL；Python 同 documentVersion manifest 要求 ETL一致 | Fake 返回 KNOWLEDGE_VERSION_CONFLICT，并核对 Java 请求定义 | 新 indexRevision，同 contentRevision |
| 禁用后重新启用 | 墓碑按 documentId+documentVersion 永久阻断；Spring enable 仍用原内容版本 | Fake 返回 KNOWLEDGE_DOCUMENT_DISABLED | 禁用针对激活/索引代际；enable 创建新激活，不能删除历史墓碑绕过保护 |
| 全库重建后单文档重新索引 | 全库共享 rebuild ETL，与单文档 ETL不同 | Fake 返回 KNOWLEDGE_VERSION_CONFLICT | buildRevision 不覆盖文档 indexRevision |
| 空集合重建 | 可重建文档为零仍允许切 alias | Fake 已切到空集合 | 默认阻止非空库被空构建覆盖；清空应是独立明确操作 |
| 替换失败后再重建 | 文档行仅登记当前 OSS 对象；候选要求 ACTIVE 且 indexedVersion=documentVersion，上一有效版本可能被排除 | 源码推导，未做跨资源复现 | 分离待处理版本与 servingRevision，登记不可变历史对象 |
| 第二次快照校验后管理员禁用/替换 | Worker 只核对两次快照，管理员 CRUD不被整个构建期冻结 | 竞态待测 | 发布前按全局变更 epoch 条件仲裁，过期构建不可发布 |
| 长 RPC越过租约期限 | 事前验 lease 不等于 Milvus 写操作原子执行 fence | 多实例待测 | 旧 owner仅能写私有候选；权威发布指针条件更新，续期仅辅助 |
| alias已切，响应/落账丢失 | 跨资源非事务；重新认领可能换操作身份 | 故障注入待测 | 稳定发布 ID、发布账本、读回对账，不把超时当未发布 |
| 问答生成期间禁用 | 请求已经取到正文；不保证点击立即影响在途回答 | 待定义并测试 | 明确请求快照语义；敏感撤销在输出前经 Spring 重验 |
| 相同维度切模型 | 维度兼容不代表向量空间兼容 | 读路径源码风险 | query 与发布清单模型签名强校验，不一致拒绝 |
| 保留旧 collection 后回滚 | 新墓碑、内容状态、模型配置可能已变化 | 待测 | 回滚是经当前规则验证的新发布，不能直接切旧 alias复活删除内容 |

上述三种拒绝是函数级实际结果与两端请求契约核对，尚未通过真实管理 API + MySQL + Milvus 全链路运行。其余竞态为风险假设，不宣称已经发生串版或泄露。

## 6. 推荐版本模型与发布边界

建议区分五种身份，避免 ETL 同时承担内容与全库构建身份：

| 身份 | 职责 | 如何变化 |
|---|---|---|
| contentRevision | 不可变原文：OSS objectKey、文件哈希、审核状态 | 替换正文新增；重试/重新索引不变 |
| indexRevision | 确定解析、切分、Embedding 签名与块集合 | 同内容重索引新增；完全相同任务重试不变 |
| activationRevision | 文档可服务资格与禁用/删除次序 | 启用/禁用改变，旧删除不能误伤新激活 |
| buildRevision / publicationId | 全库文档修订集合、集合名、总指纹 | 每个新候选/发布有稳定身份，不冒充单文档 ETL |
| attemptId / owner / fence | 一次执行及其仲裁资格 | 重试可换 attempt/owner，但不换待发布版本身份 |

原文版本 registry 必须记录历史对象引用，保留策略独立于 Milvus collection 清理。latestContentRevision 表示最新上传，servingIndexRevision 表示已验收可读版；新版本失败时保留旧 serving 指针，除非管理员明确禁用/删除。

推荐发布流程：

1. Spring 登记快照及 mutationEpoch；Python 只通过内部 API 接收内容与索引计划，不直接读 MySQL。
2. Python 在操作独占的不可变 staging 中构建，记录 parser/split/embedding 签名、内容哈希、块物理身份和完整标志。
3. Python 返回完整候选；Spring 在数据库事务内按快照 epoch、当前 owner/fence 和撤销状态条件提交 publication 与 serving 指针。候选过期就拒绝，避免仅凭“此前租约有效”切换。
4. 为避免数据库和 alias 双写不一致，新读取从 Spring 获取有界发布快照（physical collection + publicationId + 模型签名），Milvus alias作为兼容投影，由 Outbox对账。不得同时让 alias与数据库都充当独立权威；这一改动需两端整体迁移。
5. 请求绑定一个 publication；补块、相邻扩展、引用均不跨它的文档/indexRevision。禁用后新请求不取得禁用文档；在途请求是否可继续使用旧快照必须在产品协议明确。若要求即时撤销，输出前调用 Spring校验来源 activationRevision，失败拒答，仍需定义校验到响应之间的极短竞态边界。
6. 回滚作为新 publication：重验当前删除/禁用与审核规则、模型签名，不复活已撤销文档。空构建默认不可覆盖非空库；明确清空走独立管理操作。

不追求假定存在的 MySQL/OSS/Milvus 分布式事务；使用不可变候选、单一权威发布指针、幂等账本和对账处理丢响应。迁移不得通过手工清墓碑、伪造 contentVersion 或直接放宽 manifest 冲突校验来“修好按钮”。

## 7. 质量优化顺序

### P0：版本正确性

先落地重新索引、启用、重建三个身份契约和空库保护；随后实现历史原文登记、发布仲裁与故障对账。禁止将不同版本的安全改动和检索效果实验混成一个候选。

### P1：必要证据与语义结构

1. Embedding 输入显式增加有界标题路径；模型上下文可增加不可信来源标题，正文和定位保留独立字段。记录 split/embedding输入版本，变更必须重建候选索引。
2. 对照测试“同文档最多两块，总计仍三块”与现状；适合上传格式+索引生效、模板+脱敏等多事实问题。不无条件拼整份文档，也不允许旧版本补块。
3. 若采用父段/相邻扩展，限制同版本、相同章节作用域、字节与字符预算，保留原始 span与精确来源。合成新上下文不能借旧 chunkId引用未属于它的正文，须明确多块来源或父块身份。
4. DOCX尝试同章短段合并、表头连同行内容；PDF跨页仅对明确连续结构扩展。OCR作为单独能力，未开启时说明无法提取，不把空文本当已索引。
5. 保留“常见问法”作为导航/检索辅助时，需要答案链接或父章节作用域，防止只有问题列表成为最终证据；不可凭样本表现随意删除难题章节。

当前公共来源上限是三个 chunk，放入同文档不同块在结构上可表达，但改变了当前“不同文档”选择语义；旧评测的文档唯一性规则需显式区分。保持旧 v1 评分，同时新评事实支持，不偷偷修改旧分母。

### P2：由数据决定召回与阈值

先比较 Top-8 / 16 / 24，最终三块及总上下文预算固定；观察必要事实召回和重排超时，而非单纯 answered数量。仅当错误明确属于召回阶段，再引入 dense+BM25 的 RRF混合检索，针对类型名、错误码、数字、否定和权限条件评测。

多意图 query分解最多两路且共享候选预算，只有证据证明有收益再做。阈值从已标注必要/无关片段上校准，并测试否定解释和拒答边界；不能用 sigmoid 0.5作默认正确门槛。不同时改模型、切分、召回和提示。

### P3：性能与运维

先测逐文档状态 RPC占比，再考虑批量 manifest检查或按精确物理集合+发布修订缓存；失效规则与禁用边界须随方案验证。全库重建按批处理和异步任务延长执行窗口，但续期不是发布资格的最终证明。

现有重建上限还包括 1000 文档、100万块、64MiB文本、800万 embedding元素；3072维下共享向量元素预算约只容纳2604块，可能先于名义块上限触发。扩容需估算实际上限、内存和供应商成本，失败不切换。

## 8. 新评测集及实验设计

新增 `rag-boundary-study/v1` 包含：

- 32题 / 16边界对：24可答、8拒答。覆盖同文档多事实、首次失败/旧成功版本、源码与历史权限、口语类型名、公共否定解释与越权执行、私有实时状态与公开规则、素材不同入口。
- 12个语料 fixture：标题丢失、邻章互补、DOCX段落/表头、跨页PDF/扫描件、长否定句、英文句点、Unicode/JSON预算、围栏、问句干扰、废弃矛盾材料。
- 12个生命周期定义：已测输入重试及三种冲突、空库；未测替换失败、撤销在途、快照变更、租约过期、响应丢失、同维/异维模型切换、删除后回滚。

每个问答保存 sourceSections 与文件/正文哈希、expectedFacts、禁止推导的结论，待人工逐题复核。当前 questionSuite 兼容现有 `load_evaluation_dataset`；外层 fixture/lifecycle 和 expectedFacts 不能由旧 runner自动评分，后续需独立测试夹具与事实评分器。运行时将逻辑文档名映射成该快照的真实ID，必须检查版本和哈希，不能复用历史 ID盲跑。

同组近义题放同分区，当前 development / frozen-regression 是诊断与冻结回归划分；样本来自已观察问题，**不是独立未见过泛化集**。未来泛化集应由另一位审核者从新增正文与未暴露边界编写，再冻结。

实施实验阶梯：

1. 冻结当前文档哈希、真实版本映射、物理集合、query模型签名、重排器、R1提示哈希及预算；复核旧90题仍与当前正文一致。历史成绩仅作参考。
2. 离线跑 parser/selection/版本契约；隔离集合测召回及必要证据经过检索、重排、选择、裁剪各阶段的损失。先不调用回答模型。
3. 首轮只比较现状与一个证据选择候选，32题×2组×3轮 = **最多192次回答模型调用**，发送前预占额度，失败也计入；Embedding调用与输入token另外统计。真实调用总量在执行时按用户授权确定，本轮为0。
4. 固定上下文比较生成/引用策略，用来隔离模型提示因素；只有阶段证据支持才运行提示候选。E1与R1不可未经测试直接组合推广。
5. 胜出候选在当前90题和冻结回归集跑端到端，再做独立人工事实复核；按组配对统计和逐题错误清单，重复三轮不当作独立样本。

建议推广门槛：版本/禁用/串版测试零违反；新8道拒答三轮24/24满足内部契约且公共解释题不误拒；必要事实完整率不得回退；关注边界题必须消除确定性缺失，不能仅靠平均分；引用结构零非法且人工来源支持无新增错误；P95不高于同机现状20%作为首轮预算门槛，最终SLO需按实际负载决定。小样本通过只允许进入下一阶段，不称全域安全保证。
