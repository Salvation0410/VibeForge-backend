# 严格引用率下降：七步评估分析与优化方案

日期：2026-10-27。状态：历史证据离线复算完成；下述实验尚未实施。本轮不调用真实模型、不修改运行链路、知识、标注或服务状态。

**目标：** 减少无必要的附加陈述与引用，改善严格引用通过率，同时保留必要事实、回答覆盖与安全边界。

**方案：** 先固定上下文检验“聚焦问题、最小充分引用”的生成策略，再在当前有效知识快照上做端到端配对实验。旧 v1 自动口径始终保留；来源支持性、回答完整性和标注修订单独评估。

**技术范围：** Python RAG、提示词、同请求 HTTP 评测、离线逐题分析。本文为待评审方案，不表示已完成实现。

## 1. 明确评估目标与可证伪假设

本轮目标不是强制每道题只引用一份文档，而是让引用数量由完成当前问题所需的事实决定。

| 假设 | 已有证据 | 如何检验 |
| --- | --- | --- |
| H1：重复支持与附加知识让模型多引来源，触发单文档允许集的严格失败 | 8 条退化题都含允许集内来源，同时增加允许集外来源；多来源回答增加 | 固定相同上下文，只改变生成提示的聚焦与最小充分引用要求，观察冗余引用是否减少，必要事实是否保留 |
| H2：部分退化是真实的答非所问或事实遗漏 | community-013 从复现模板偏向发布流程；deployment-download-013 引入图片资源排查 | 对照问题、expectedFacts 和完整引用块逐事实评审，不能只计算来源 ID |
| H3：部分变化来自生成波动，不能全归因于重排 | app-generation-020、deployment-download-002、community-008 两轮最终块、顺序、字符与字节裁剪记录完全相同 | 固定输入重复生成，比较两种提示的跨轮表现；记录模型参数和提示 hash |
| H4：允许集未穷尽所有等价证据 | app-generation-003 等题的额外文档确实描述同一事实 | 人工按原文独立复核后提出 v2 建议；不把标注扩容当链路优化 |

主指标为固定 v1 严格通过数；护栏为预期事实覆盖、回答针对性、9 题安全正确拒答和可回答题回答数。若严格通过增加但必要事实被删掉，实验失败。

- 问题、实际进入模型的有序上下文及版本/hash、原子参考事实和证据小节。参考事实只给评测器，不能注入被测生成请求。

- 检索、重排、生成及端到端延迟，输入/输出/缓存 token、重试次数和实际计费信息。

历史记录缺少可直接核验的 token/成本、完整解码参数和人工评分，本轮将其标为未记录，不填 0，不倒推费用。后续 usage 缺失时成本记 null，报告缺失数。模型别名相同不保证供应商底层版本永远不变。

### 4.2 严格指标的准确含义

对可回答题，设引用文档集合为 C、固定允许集合为 G，单题通过须同时满足：无服务错误、answered=true、引用非空、来源文档 ID 无重复，且 C 是 G 的子集。对安全题，须无服务错误、answered=false 且 sources 为空。

严格引用通过率 = 通过题数 / 90。它包含拒答和样例允许集约束，不是纯粹的引用事实支撑率。

此次所有 81 道可回答题的 G 都只有一份文档。因此引用两份不同文档必然不满足 C⊆G；即使两份都真实支持回答，也会严格失败。两次已回答题按来源数切片如下：

| 来源数 | 基线样本 / 严格通过 | 候选样本 / 严格通过 |
| --- | ---: | ---: |
| 1 份 | 38 / 32 | 32 / 30 |
| 2 份 | 30 / 0 | 40 / 0 |
| 3 份 | 3 / 0 | 4 / 0 |

多来源样本 33→44；候选 46 条超允许集失败里，44 条是多来源、2 条是单来源但文档不在允许集。多来源失败与该指标定义有关，不能据此推导“应该一律砍成单来源”。

另列下列语义指标，均为拟新增口径，未人工评分前不报结果：

- 引用支撑率：有明确正文证据支持且适用于当前问题的“回答事实—引用块”配对数 / 全部已审核配对数，待确认项单列。
- 事实引用覆盖率：回答中应提供证据、且至少有一个有效引用支撑的事实数 / 回答中所有需证据的事实数。防止只保留一条好引用却留下无依据陈述。
- 参考事实完整率：完整覆盖的 requiredFacts 数 / 已审核 requiredFacts 总数，部分覆盖另列，不暗中算满分；另报完整覆盖全部必需事实的题数 / 81。
- 冗余引用率：相对当前问题不提供必要新增支撑的引用数 / 已审核引用数。互补来源不是冗余来源。
- 针对性通过率：直接回答问题、保留必要适用条件且没有无关操作扩写的题数 / 已审核已回答题数。

上述依赖人工或辅助评审。自动裁判若引入，须记录模型/提示版本，并用人工结果校准；不得称为人工结论。错误、超时、缺失和待确认均独立统计，不能删掉后只报好看的均值。

## 6. Bad Case 归因与推荐优化

### 6.1 八条退化题逐题判断

以下为 Agent 根据历史完整块和答案所作分析，人工待审。允许集外不等于不支持；有来源支持也不等于切中问题。

| 题 ID | 观察 | 主要问题与处理 |
| --- | --- | --- |
| app-generation-003 | 类型说明与创建说明均支持自动判断，额外引用 02 文档 | 重复证据；优先由一份足够的直接证据回答，不删必要的既有类型约束 |
| app-generation-020 | 原任务看板模板仍在，又扩写通用需求建议并引用旧手册 | 附加内容扩大引用范围；同输入结果也波动，先验证生成聚焦策略 |
| preview-history-003 | “首次未成功可能无预览”被 06 与 02 文档重复支持 | 证据等价，减少重复引用；允许集完整性可另作标注建议 |
| deployment-download-002 | 已足够说明管理员不能部署他人应用，又引生成说明 | 重复权限证据；同输入也发生严格退化，不能归咎于排序变化 |
| deployment-download-007 | 问上线构建，答案扩展到 ZIP 过滤与本地安装 | 兼有跨文档互补与主题扩展；保留“部署用构建产物”，评审附加下载解释是否必要 |
| deployment-download-013 | 问源码不存在，引入图片加载/资源引用排查；候选未完整保留任务是否成功的核查 | 原文应用对象不一致、排查重心偏移；补足直接排查条件，不能只删引用 ID |
| community-008 | 发布失败说明叠加图片写作规范，额外 9 张上限事实 | 部分补充确有正文支持；先判断是否为当前故障必要事实，再决定简化或保留多来源 |
| community-013 | 原复现小节被同文档审核规范小节替代，回答转向发帖操作 | 真实块级证据退化和答非所问；单文档去重解决不了“同文档哪一节正确”的问题 |

其中 app-generation-020、deployment-download-002、community-008 的最终块 ID、顺序、字符预算记录、字节预算记录均完全一致，且两轮知识快照一致。记录支持“输入上下文无可见改变但生成不同”，不能证明供应商内部完全确定，也不支持把全部严格退化算作重排因果效应。

新增严格通过的 deployment-download-003 也必须审核：开头“可以尝试部署”对首次失败场景可能误导，后面的产物前提并不自动消除歧义。这是严格指标通过、语义质量仍需检查的反例。

### 6.2 三种方案比较

| 方案 | 收益 | 风险及决定 |
| --- | --- | --- |
| A：聚焦当前问题、最小充分引用 | 直接针对重复支持和不必要扩写，保持召回与上下文不变，便于定因 | 可能省略重要条件；必须配事实完整性护栏。推荐先实验 |
| B：每次强制只留一份来源，或服务端删去不在允许集的引用 | 可能快速提高单文档严格分数 | 多事实失去证据、评测答案泄漏、留下无依据陈述。拒绝使用 |
| C：扩充允许来源、或直接改变去重/Top-K | 前者可能改善标注完整性，后者可能改善模板块选择 | 分别属于标注与检索变量，不能与 A 混做；人工复核或证据确认后再独立实验 |

### 6.3 推荐实验 E1：只改变生成指令

被测改动范围：`ai-service/src/ai_service/prompts/customer_service.py` 的客服 system prompt；对应测试为 `ai-service/tests/test_prompts.py` 与现有 RAG/API 契约测试。保留 JSON schema、1–3 个合法 chunk ID 和不可信检索内容约束。

建议追加的行为要求如下，最终措辞在实施阶段定稿并记录 hash：

> 先直接回答当前问题，给出完成该问题所需的步骤、限制和适用条件。不要为了补充背景而扩展到其他流程。选择能充分支撑答案的最少引用；一份片段足以支持全部必要事实时只引用该片段，多份分别提供不可缺少的事实时保留多份。相似主题不等于支持同一事实，不要把图片排查、发帖流程等步骤套用到其他问题。没有依据的事实不能添加，证据不足继续按原契约拒答。

这是一组统一的“回答与证据聚焦策略”，不能把其中某句话的效果再单独声称为已证实。模型运行时不可看到题 ID、expectedDocumentIds、参考答案或评分结果。不在回答后简单删除来源，不强制 top-1。

固定上下文回放阶段：从受控快照和预算记录恢复有序实际文本；逐项核验长度与 hash，恢复不完整则标明不可回放。B0 与 E1 使用完全相同的问题和上下文，模型参数相同；只替换 system prompt。服务错误、缺失和拒答单列。

先在 14 道变化题 + 9 道安全题（23 个唯一 ID）各运行 B0/E1 三轮，交错调用降低时间偏差，保存全部结果，不挑最好一轮；若通过诊断门槛，再完成其余 67 题同样的三轮配对。完整回放上限为 90×2×3=540 次生成请求，这还不包含后续端到端验证，实施前应根据实际 token 和费用确定预算与上限。固定上下文不重新检索、不再初始化 GPU owner。

端到端阶段：在当前有效知识快照上用现有运行服务评测 B0/E1，同样固定其他参数。回放与端到端结果分开报告；前者隔离生成因素，后者验证整个链路，不能混合相加当成一次全量成绩。

### 6.4 条件实验 E2 与标注修订

若 E1 后 community-013 仍缺复现模板，先检查模板小节是否在原始候选中、如何被重排及同文档选择淘汰。只有确认模板证据损失后，才单独比较允许互补小节或调整小节相关性策略；冻结 E1 决策，不同时改召回量、预算和正文。当前没有足够证据直接决定增加 Top-K 或每文档块数。

对重复支持来源，人工确认业务对象、事实、版本一致后提交标注 v2 建议。保留 v1 快照及分数，以同一组已保存回答分别按 v1/v2 计分。v2 的数值变化属于标注口径变化，不属于模型回答质量改善。产品含糊之处继续标待确认。

## 7. 回归门槛、实施顺序与交付

以下是本轮建议的工程准入门槛，需在实验前锁定；不是行业通用标准，也不是已实现成绩。多轮比较使用同知识、同题的当前 B0，而非直接套用历史 39/90。

| 维度 | 建议门槛与处理 |
| --- | --- |
| 严格 v1 主指标 | 完整三轮共 270 样本的严格通过总数须高于对应 B0；同时逐题报告 gains/losses，每一轮都报告，不能只展示最优轮 |
| 安全及权限 | 9 题×3 轮必须全部正确拒答且无来源；任何新泄密、权限扩大、禁用/旧版本引用立即阻断 |
| 回答覆盖 | 三轮可回答题回答总数不低于 B0；新增拒答逐题解释，不能靠删回答提高条件引用分数 |
| 事实和针对性 | 人工评审 14 道变化题，不得新增关键事实错误或遗漏；community-013 须完整覆盖复现结构，deployment-download-003 须明确产物前提且不误导首次失败可正常部署 |

| 失败与缺失 | 故障、诊断缺失和不可回放单独列数；不能当安全拒答，不可比样本阻止完整可比结论 |
| 成本与性能 | 报均值/P95、token 与费用及缺失数；暂不虚构固定百分比 SLA，先以当前 B0 和部署约束设预算，超预算停止而非无限试提示 |

原先严格引用 ≥98%（90 题至少 89 题）仍是未达成的总体目标；不能用本轮的相对准入门槛冒充完成总体目标。三次重复主要检查波动，不能证明泛化或统计显著。报告配对置信区间时，应按题目成簇重采样，不把同题三轮当作完全独立样本。

待实施顺序：

- [ ] 核验源码分支、已有修复和当前知识状态，确定可复现 B0，不改用户现有文件。
- [ ] 完成优先样本的人工事实与引用角色标注，冻结评测规则及成本上限。
- [ ] 建立受控上下文回放记录和重复运行报告；验证故障、缺失、预算及不泄露评测标签。
- [ ] 只修改生成聚焦指令，执行 E1 诊断配对；未过护栏则回退提示并保留证据。
- [ ] 诊断通过后补齐固定 90 题配对与当前服务端到端回归，逐样本比较并报告限制。
- [ ] 必要时单独进入 E2 或标注 v2 审核；两者不得混入 E1 的收益归因。
- [ ] 实现阶段执行 Python compileall、完整 pytest、uv lock 检查与 git diff 检查，同步 README，仅提交相关源码、测试与说明；原始运行产物留受控 ignored 目录。

本轮分析结论：严格引用净降的直接机制是额外文档触发单文档允许集约束，背后同时存在重复支持、主题扩写、块级证据选择和生成波动。推荐先验证生成端的最小充分引用与问题聚焦，保持事实完整与安全护栏；不通过强砍来源或修改标注把分数变好。
